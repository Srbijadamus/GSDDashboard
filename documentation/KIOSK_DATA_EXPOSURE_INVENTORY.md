# ShiftKiosk — Data Exposure Inventory (AS-IS)

> **STATUS 2026-10-02 — a hardening branch now exists.** This document describes the
> system AS IT RUNS TODAY, which stays accurate until the branch is deployed. What
> changes, in what order, with rollback per item, is in
> [KIOSK_HARDENING_DEPLOY_NOTE.md](KIOSK_HARDENING_DEPLOY_NOTE.md).
> Branch `security/kiosk-hardening` in `C:\ShiftKiosk_secure` + `C:\GSDDashboard_secure`.

What personal data each readable endpoint of the ShiftKiosk server returns, and which
endpoints return data about **people other than the caller**. Derived from the SQL in
`C:\ShiftKiosk\server\server.py`; auth per endpoint is in
[KIOSK_ENDPOINT_ACCESS_MATRIX.md](KIOSK_ENDPOINT_ACCESS_MATRIX.md).

**The headline finding, CONFIRMED:** *every* readable endpoint returns data about all
agents. **No endpoint is scoped to the caller**, because no endpoint knows who the caller
is ([KIOSK_AUTH_IDENTITY_ASIS.md](KIOSK_AUTH_IDENTITY_ASIS.md) §2, §4). There is no
"own data only" path anywhere in the kiosk server.

## 3. Special categories and retention

| Item | Finding |
|---|---|
| Health-related data | CONFIRMED — `SICK_LEAVE` is a first-class status (`server.py:1002`) stored per event in `status_log.status` and surfaced as `attendance_status='SICK'` by the **unauthenticated** `/api/attendance` (`server.py:409`). `/api/history` returns the full `SICK_LEAVE` history for everyone. A record of who called in sick, and when, is one of the most sensitive items in the system and is the least protected. |
| Notification side-channel | CONFIRMED — `SICK_LEAVE` and `EMERGENCY` events generate a Teams card and an e-mail with the agent's real name and team leader in the subject (`server.py:1025-1038`), subject to `notify_sick_leave` (`server.py:38`). Recipients are configured in `server_config.ini` `[Email] recipient_email` — a single static address, not the agent's own team leader. |
| Device tracking | CONFIRMED — `agent_hostname` is recorded per event (`server.py:100`), giving a per-machine movement trail. |
| Retention / deletion | NOT FOUND IN CODE OR DOCS — there is no purge job, retention setting, or delete endpoint for `status_log` or `manual_actions` anywhere in `server.py`. `/api/history` is unbounded by default and `/api/audit-log` has no date filter at all (`server.py:490-496`), which is consistent with unlimited retention. |
| Free-text notes | CONFIRMED — `note` is agent-supplied on `POST /api/status` (`server.py:965`) with no length limit or content filter beyond Pydantic's `str`, and is returned by the open `/api/attendance` as `status_note` (`server.py:415`). |

## 4. Which endpoints return data about users other than the caller

CONFIRMED — **all of them**, with the sole partial exception of the three kiosk lookups
(`/api/agent-lookup`, `/api/shift-status`, `/api/agent-location-options`), which return
data about *one* agent — but about **whichever** agent the caller names, not the caller.

There is no endpoint, parameter, or code path that restricts a response to the
authenticated caller's own record. That is not a configuration gap: the credential carries
no subject, so such a restriction cannot be expressed in the current design
([KIOSK_AUTH_IDENTITY_ASIS.md](KIOSK_AUTH_IDENTITY_ASIS.md) §2 item 4).

This is the concrete reason why "stop returning other users' data to a kiosk"
(Phase 0 in [SECURITY_MIGRATION_PROPOSAL.md](SECURITY_MIGRATION_PROPOSAL.md)) requires an
authenticated subject first, and cannot be done by filtering alone.
