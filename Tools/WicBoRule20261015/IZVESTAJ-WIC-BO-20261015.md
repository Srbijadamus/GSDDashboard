# WIC has priority over BO — owner rule 2026-10-15

Task: replace "a BO row is never WIC" (commit `84e71e4`) with the owner's rule:

> **BO = Back Office. WIC has PRIORITY over BO.** An agent with an ACTIVE WIC assignment
> (MAIN / BACKUP / REGIONAL) whose plan says BO goes to WIC — UNLESS RTM set BO on that day
> **by hand**, in which case BO stands. The centre's working hours always apply:
> WIC presence = the agent's shift ∩ the centre's working window (`WicHoursResolver`).

## 1. Analysis (read-only)

### 1.1 Where the manual-change history lives — and what does NOT exist

There is **no dedicated audit/history table or log for `ShiftEntries`**. Verified from four
independent sources, not assumed:

| Evidence | What it shows |
|---|---|
| `Backend/GSDContext.cs:231-255` | The complete EF model. The only `ShiftEntries` DbSet; **no** history/audit/revision entity. |
| `Backend/Program.cs:213-604` | Every table the app creates on startup (idempotent DDL). No history table. |
| live `sys.tables` | 53 tables: the app's own, `__EFMigrationsHistory`, and 17 `ShiftEntries_bak_*` / `WicShiftEntries_bak_*` **point-in-time copies** from earlier repairs. No `%history%`/`%audit%`/`%log%` table for shift rows. |
| `documentation/LIVE_DEPLOY_RUNBOOK.md` (lines 372-373) | "No temporal/CDC/change-tracking/trigger row history exists, and the available transaction log returned no retained transaction groups for that window." |

The authoritative evidence of a manual change is therefore **in the row itself**:

* `ShiftEntries.ManualChangeBy` / `ManualChangeAt` / `ManualChangeNote` — the manual marker
  (`GSDContext.RecordManualShiftEdit`, `:30-40`; `IsManualChange`, `Backend/ShiftEntry.cs:48`).
  Automation can never overwrite such a row (`GuardManualShifts`, `GSDContext.cs:82-98`).
* `ShiftEntries.AutoGenerated`, `SourceModule`, `SourceId`, `PreviousStatus` — provenance.
* Per-writer audit *around* the row: `RosterBatches` (automatic generator batch, incl.
  `ReplacedRowsJson` pre-image), `RtmEntries` (Bulk RTM paste staging list — per **day**, not per
  ShiftEntries row), `BoEntries` (BO List page), and the `ShiftEntries_bak_*` copies.

**How "did RTM manually set BO?" is decided.** Only the *automatic* roster generator ever writes
`RawValue="BO"` (`RosterService.ApplyGenerated`, `RosterService.cs:1113-1118`; `ShiftUpdateDto` /
`AssignShiftDto` have no RawValue field), and the manual Shift Plan API accepts the literal
`ShiftType="BO"`. So:

* **manual RTM BO** = a BO day (`RawValue='BO'` on `WORKING`, or literal `ShiftType='BO'`) **with
  `ManualChangeBy` set** — the human authored/confirmed the day and it is a back-office day;
* **plan BO** = the same shape with `ManualChangeBy` NULL — the automatic generator's day, so the
  WIC priority rule applies;
* a real `WIC_DUTY` row stays WIC duty whatever its leftover `RawValue` says (type is authority).

### 1.3 Row 57736 — 9119463, Mülheim, 2026-10-29

```
Id=57736  EmployeeId=9119463  Jonathan Freudenthaler  ShiftDate=2026-10-29 (Thursday)
ShiftType=WORKING   RawValue=BO   AgentTask=Mülheim   IsWicDuty=0   AutoGenerated=0
SourceModule=Roster SourceId=211   ManualChangeBy=S60028
ManualChangeAt=2026-10-05T13:45:41.055  ManualChangeNote="Manual shift cell edit (/shifts); …"
```

* **Who/what created the day.** `RosterBatches` **Id=211**, `CreatedByKid=SYSTEM_BACKUPFIX`,
  `CreatedAt=2026-09-30 06:31:08`, `DateFrom=DateTo=2026-10-29`, `RowCount=1`,
  `LocationCode=DE~45476~Mülheim~Moritzstr. 16-22`, `AgentTask=NULL` → the automatic batch wrote
  exactly this one row as a back-office day (`RawValue='BO'`, `AgentTask` null).
* **What RTM did.** On 2026-10-05 13:45:41 **S60028** manually edited that row (Shift Plan cell):
  the row is `AutoGenerated=0`, carries the manual marker and the manual note, and the type is
  `WORKING` with `AgentTask='Mülheim'` — i.e. **RTM set the day to back office**. It is one of 12
  `S60028` rows for this employee (the whole 13:43-13:45 session), and it is the only one whose
  `AgentTask` still carries the centre name.
* **Verdict: RTM manually set BO on 2026-10-29 → BO stands → the day is NOT WIC.** The row was
  therefore deliberately **excluded** from the data migration (it is not in `plan.csv`), and the
  new reader returns `false` for it (`WicBackOfficePriority.IsManualBackOffice`).
* **Why `/api/wic/open` reports `UNCOVERED 0/0`.** `GET /api/wic/open` (`WicShiftService.GetOpenAsync`,
  `:223-328`) is **signal 1 only**: it counts `WicShiftEntries` rows with `IsOnSite=1` for the
  location+date. On 2026-10-29 9119463 has **no** on-site WIC row at Mülheim (BO stands), and
  nobody else does, so the response is verbatim:

  ```json
  { "locationCode": "DE~45476~Mülheim~Moritzstr. 16-22", "displayName": "Mülheim",
    "isOpen": true, "openIntervals": [ { "openTime": "08:00", "closeTime": "12:00" } ],
    "coverageStatus": "UNCOVERED", "scheduledCount": 0, "absentCount": 0,
    "effectiveCoverage": 0, "minRequired": 1 }
  ```

  The "0/0" is the **scheduled=0 / absent=0** pair — zero agents on site and zero absent. The
  centre is OPEN (Thursday 08:00-12:00, `MinRequired=1`), which is why it appears at all and why
  its real grade is `UNCOVERED 0/1`. It is not a data defect: it is the consequence of RTM's own
  BO decision, which the owner rule says must stand.

## 2. Code changes

One shared definition, used by every reader; the centre of a plan BO day comes from the agent's
assignment, never from a stale `AgentTask`.

| File | Change |
|---|---|
| **`Backend/Services/WicBackOfficePriority.cs`** *(new)* | THE rule. `IsBackOfficeDay` / `IsManualBackOffice` / `IsPlanBackOffice`; `WicAssignmentIndex` (employee → ordered active MAIN/BACKUP/REGIONAL centres, matched by `EmployeeName == FullName` + `MatchesAssignmentCode`); `PriorityCentre` (first tier with open centres, exactly one open centre — 2+ is ambiguous and stays BO, the generator's no-guess rule); `IsPlanBackOfficeWicAt`; `RuleMarker = "RTM_RULE 2026-10-15 WIC>BO"`. |
| `Backend/Services/AvailabilityResolver.cs` | `IsWicDutyAt(sh, loc)` rejects only **manual** BO; new assignment-aware overload `IsWicDutyAt(sh, loc, index, hours)` resolves a plan BO row to its priority centre. `GetWicContributionAt` / `GetOnSiteWicContribution` gained the same context (and a plan BO row scores 1.0 in the on-site reading, because the agent IS staffing the centre). |
| `Backend/Services/WicPresenceResolver.cs` | `CandidateDutyRows` now keeps **plan** BO rows (even without an AgentTask) and drops only manual BO; `Resolve` takes the assignment index + opening hours and uses the shared overloads. |
| `Backend/Services/WicBackOfficeSync.cs` *(new)* | Creates/keeps the on-site `WicShiftEntries` row for a plan BO row, `WorkingShift = WicWorkingShift.Slice(shift, centre window) ?? FallbackWindow`. Sees tracked-but-unsaved employees/centres/hours and revives a row another writer is deleting in the same unit of work. |
| `Backend/GSDContext.cs` | `SaveChanges`/`SaveChangesAsync` call the new sync **in the same unit of work** for every Added/Modified plan BO row — the shift-plan→WIC sync, covering the generator, imports and every later writer. The previous rule (a stale centre name is cleared only on a MANUAL RTM WIC_DUTY→WORKING/BO edit) is unchanged. |
| `Backend/WicCoverageGapService.cs` | SQL signal-2 pre-filters (both) now drop only **manual** BO and keep plan BO rows; the assignment index is built once and passed to `ComputeCoveredDates` / `PresenceFor`; `ComputeTaskLabel` labels a convertible plan BO row as the WIC duty at its priority centre, not "BO". |
| `Backend/WicCardsService.cs` | Builds the index; a plan BO day no longer gets the "GSD" non-WIC marker; `Resolve` receives the index + hours. |
| `Backend/Services/ForecastService.cs`, `BriefingService.cs` | Load the active assignments/employees, build the index and pass it (with all opening hours) to `Resolve`. |
| `Backend/WicShiftService.cs` (GetOpen), `OverviewService`, `BackupService` | No signature change needed: they read signal 1 through `GetOnSiteWicContribution`, which now scores a plan BO day 1.0. |

Nothing overwrites manual edits, AL/SL/UL/OL/PH/LPH, HALF_AL, OFF/OFF_WEEKEND, TRAINING or any
row with `ManualChangeBy` — `GuardManualShifts` (`GSDContext.cs:82-98`) and
`IsManualBackOffice` both enforce it, and the generator's BO branch is deliberately **not**
rewritten: the on-site WIC row carries the commitment (the WIC>BO artefact the task asked for).
