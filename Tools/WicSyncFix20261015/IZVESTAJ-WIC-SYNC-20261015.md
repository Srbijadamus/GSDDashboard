# WIC shift-plan sync — a `WIC_DUTY` row must have its on-site WIC row (2026-10-15, follow-up)

**Defect.** A `ShiftEntries` row that carries a WIC duty had no on-site `WicShiftEntries` row,
so the two coverage readings of the very same day disagreed:

* `GET /api/wic/cards` (and the forecast / gap detector) read the **ShiftEntries** row through
  `AvailabilityResolver.IsWicDutyAt` → **COVERED**;
* `GET /api/wic/open` is **signal 1 only** — it counts `WicShiftEntries` rows with
  `IsOnSite = 1` → **UNCOVERED**.

Live example: employee **9074345**, Wesel, 2026-11-05 / 11-12 / 11-19 / 11-26, `RosterBatch 265`.

Everything below is from the working tree `C:\GSDDashboard_secure`, SDK **10.0.204**, against the
live database `GSDDashboard` on `localhost\SQLEXPRESS`. No test account was used; every login was
the DEV operator KID **S69307**. **The RTM KID `S60028` was never used for a login or a write** —
it only appears as the pre-existing `ManualChangeBy` value already on rows (never written by this
task). Identifiers are EmployeeIds only: no employee name appears in this report.

### 1.2 The code path that wrote `WIC_DUTY` without the sync — file:line

As deployed (`HEAD` = `b03e379`, built 2026-10-15 19:35):

1. **`Backend/RosterService.cs:1244`** — the generator's OVERWRITE branch removes the day's
   `WicShiftEntries` rows (`_db.WicShiftEntries.RemoveRange(wicRows)`) when the row it replaces was
   `WIC_DUTY`; it does this *before* the replacement row is shaped.
2. **`Backend/RosterService.cs:1256`** — the branch then calls the local upsert
   **`Backend/RosterService.cs:1138-1168`** for the regenerated WIC day.
3. **`Backend/RosterService.cs:1140`** — `_db.WicShiftEntries.FirstOrDefaultAsync(...)`. EF Core
   returns the **still-tracked** entity from step 1, and that entity is in state **`Deleted`**.
4. **`Backend/RosterService.cs:1146-1151`** — the method writes `WorkingShift`, `LocationCode`,
   `IsOnSite = true` … **into that already-deleted instance** and never revives it
   (`EntityState.Deleted → Modified`, which `WicBackOfficeSync` does at its line 122-123).
5. `SaveChangesAsync` therefore **deletes** the row. The `ShiftEntries` row keeps
   `ShiftType = WIC_DUTY`, so `/api/wic/cards` reads COVERED while `/api/wic/open` — on-site rows
   only — reads UNCOVERED.

**Evidence (the batch itself).** `RosterBatches.ReplacedRowsJson` of batch **265** stores, for each
of the four Thursdays, the pre-image `WIC_DUTY / AgentTask=Wesel / 08:00-12:00 / wic=2` — i.e. two
`WicShiftEntries` rows existed before the batch. After it, the day has **none**, and the regenerated
`ShiftEntries` row (06:00-16:00, centre 08:00-12:00) is the only record left. `RowCount = 0`,
`ReplacedExisting = 21` on the batch confirms the overwrite path.

**The 18 flipped rows** came from the same overwrite family plus later manual writes:
`Backend/RosterService.cs:1124` (`ApplyGenerated`: `AgentTask` is taken from the plan row while
`ShiftType` stays `WORKING` for a non-WIC kind) is how the SYSTEM_WICFIX/SYSTEM_BACKUPFIX batches of
2026-09-30 left `WORKING` + centre-name rows, and `Backend/ShiftService.cs:378-396` is the writer
that stands the day's on-site rows down when a row leaves `WIC_DUTY` while `AgentTask` — deliberately
— keeps the centre as the trace of a temporary move. `AvailabilityResolver.IsWicDutyAt` still reads
that shape as **WIC duty at that centre**, which is why the same open-vs-cards split applied to them.
The current writer shape for those rows is gone (the generator no longer emits it), so this is a data
repair, not a second code change.

## 2. Code

One shared sync, used by the writer that was broken **and** enforced centrally for every other
writer — the same enforcement point the WIC-over-BO rule and `LinkWicRowsToShiftTypeChanges` use.

| File | Change |
|---|---|
| **`Backend/Services/WicShiftPlanSync.cs`** *(new)* | THE Shift Plan → WIC sync for a `WIC_DUTY` row. `Apply` (for the `SaveChanges` hook) and `EnsureOnSiteRow` (for a writer that knows the day's decided window). It reuses the existing rules — no new ones: `WicWorkingShift.Slice`/`FallbackWindow` (agent window ∩ centre window, centre window when they do not touch), `WicHoursResolver` (`IsOpenOn` / `CentreWindow`; a **closed centre gets no row**), `WicLocationMatcher` (the row's centre is the one its `AgentTask` names — never guessed). A row the same unit of work is **deleting is revived**, never duplicated (`(EmployeeId, ShiftDate, SupportLocation)` is unique); an already-correct row is left untouched (idempotent). |
| `Backend/GSDContext.cs` | `SyncWicRowsForWicDuty()` called from `SaveChanges` / `SaveChangesAsync` right after the WIC-over-BO sync: every **Added/Modified** `WIC_DUTY` row gets its on-site row in the SAME unit of work — generator, overwrite path, imports and every later writer. |
| `Backend/RosterService.cs` | The generator's local upsert (the broken code path, §1.2) is deleted; it now calls `WicShiftPlanSync.EnsureOnSiteRow(..., cutToCentreWindow: false)`, because the plan segment IS the day's decided slice (`SegmentFor` already cuts the agent's shift to the centre window; the repeated multi-centre decision of 2026-10-12 is replayed verbatim). |

Deliberately unchanged (pinned behaviour, no new rules):

* **Multi-centre span** — the daily `ShiftEntries` row is widened by the writers that own it
  (`WicShiftService` / `ShiftService` via `WicWorkingShift.WidenDaily`); the sync **never re-times an
  existing on-site row** (the day row of a multi-centre day is a span across the centres and would
  destroy a centre's own slice — the 2-open-MAIN Demmin case).
* **HALF_AL** — a WIC duty on a half-AL day keeps the row `HALF_AL` and the on-site row carries the
  working part cut to the centre window; this sync never re-types a row and never touches HALF_AL.
* The flipped `WORKING` + centre encoding is **not** propagated by the hook: `LinkWicRowsToShiftTypeChanges`
  stands the on-site rows down when a writer takes a row off `WIC_DUTY`, and that documented
  "temporary move keeps only the AgentTask trace" behaviour stays as it is (its 18 legacy rows are
  repaired in the data, §3).
* Absences, training, OFF, a manual RTM BO day and plan BO rows are untouched
  (plan BO is `WicBackOfficeSync`'s business).

### 6.3 The 188 "grade-only" differences — explained as one class

188 (date, centre) pairs where **both** endpoints say the centre is staffed but grade it
differently: `COVERED`(open) vs `PARTIAL`(cards) 122 ×, `PARTIAL`(open) vs `COVERED`(cards) 66 ×.
They are the **same 188 pairs before and after** — this task changed nothing about them.

* `/api/wic/open` grades by **agents vs `MinRequired`** (`WicShiftService.GetOpenAsync` →
  `CoverageEvaluator.Classify(isClosed, effectiveCoverage, minReq)`), where each on-site agent
  scores 0.5 (HALF_AL) or 1.0;
* `/api/wic/cards` grades by **minutes vs the centre's open window**
  (`CoverageCalculator.Calculate` / `CalcAgentCoverage`), so one agent whose window does not span the
  whole opening time makes the card `PARTIAL` while the centre is still fully staffed for open's
  count.

Affected centres and counts (all 82 dates 2026-11-02 … 2027-02-26; per-row list in
`Verify/wicsync-mismatches-AFTER.csv`): Augsburg 82, Essen - BP1 43, Rendsburg 32, Essenbach 23,
Brokdorf 3, Zwolle 3, s-Hertogenbosch 2.

Worked example — **Augsburg 2027-01-08**: open COVERED (1 scheduled / 1 effective / min 1);
cards PARTIAL because the only on-site agent (9112561) covers 450 of the 480 open minutes. Both
surfaces agree the centre is staffed; only the grading unit differs. Example of the other
direction — **Essen - BP1**: open PARTIAL (its agent count is below `MinRequired` while agents are
present), cards COVERED (the open minutes are fully covered).
